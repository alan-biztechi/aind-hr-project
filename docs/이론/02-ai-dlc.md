# 02. AI-DLC: AI 주도 개발 생명주기

> **이 챕터의 목표**
>
> - DLC가 가리키는 AI-DLC가 무엇인지 이해한다.
> - AI-DLC의 단계(생명주기)를 설명할 수 있다.
> - Kiro의 기능들이 AI-DLC 철학을 어떻게 제품화했는지 연결 지을 수 있다.

---

## 1. DLC, 그리고 AI-DLC

DLC는 **Development Lifecycle**(개발 생명주기)의 약자입니다. 소프트웨어가 "기획 → 설계 → 구현 → 테스트 → 배포"로 이어지는 전체 과정을 뜻합니다.

**AI-DLC**(AI-Driven Development Lifecycle)는 AWS Labs가 제안한 개념으로, 이 개발 생명주기를 **AI 코딩 어시스턴트가 사람 개발자와 똑같은 프로세스를 따르도록 강제하는 틀**입니다.

> 한 줄 요약: AI에게 코드를 자유롭게 쓰게 두지 말고, **"이 절차대로 개발해"** 라고 규칙을 부여하는 것.

Kiro의 설계 철학이 바로 이 AI-DLC에서 나왔습니다. 그래서 AI-DLC를 이해하면 "Kiro의 기능이 왜 이렇게 생겼는지"가 보입니다.

---

## 2. 왜 AI에게 "프로세스"가 필요한가

[01장](./01-kiro-란.md)에서 본 바이브 코딩의 문제를 떠올려 봅시다. 설계·테스트·보안·일관성이 빠지는 이유는 AI가 "일단 동작하는 코드"를 목표로 삼기 때문입니다.

사람 개발팀은 이런 문제를 **프로세스**로 막습니다. 요구사항을 정리하고, 설계를 리뷰하고, 테스트를 짜고, 코드 리뷰를 거칩니다. AI-DLC는 **이 프로세스를 AI에게도 그대로 적용**하자는 발상입니다.

```
사람 개발팀의 프로세스  →  AI에게도 동일하게 강제  =  AI-DLC
```

---

## 3. AI-DLC의 단계

AI-DLC는 개발을 다음 단계로 나누고, 각 단계마다 사람의 검증 지점을 둡니다.

| 단계             | 하는 일                                  | 사람의 역할                             |
| ---------------- | ---------------------------------------- | --------------------------------------- |
| 1. 요구사항 정의 | 무엇을, 어떤 기능이 필요한지 명확히 한다 | "그냥 만들어"가 아니라 요구사항을 제시  |
| 2. 설계          | 아키텍처·데이터 모델·API 설계 결정     | AI 제안을**검토·승인**           |
| 3. 구현          | 설계에 따라 코드 작성                    | 규칙(Steering)에 맞는 일관된 코드 확인  |
| 4. 테스트        | 구현 코드에 대한 테스트 작성             | 커버리지 기준 등 확인                   |
| 5. 리뷰          | 생성된 코드를 사람이 검토                | AI가 "끝났다" 해도 사람이 확인해야 완료 |
| 6. 배포          | 테스트·리뷰를 통과한 코드 배포          | 자동 파이프라인으로 안전하게 릴리스     |

> 핵심 원칙: **AI가 "완료"라고 말해도, 사람이 확인하기 전까지는 완료가 아니다.** 중요한 결정 지점마다 사람이 개입합니다.

### 설계 단계 검토의 가치 (예시)

"사용자 인증 기능을 만들어줘"라고 요청했다고 합시다.

- **바이브 코딩**: AI가 토큰 만료를 임의로 24시간으로 잡아 코드를 생성 → 나중에 보안 요건(1시간)에 안 맞아 재작업.
- **AI-DLC**: 설계 단계에서 "토큰 만료 24시간" 제안을 보고 "우리는 1시간이어야 함"을 바로잡음 → 재작업 방지.

설계 단계에서 한 번 짚으면, 구현 이후의 대규모 수정을 막을 수 있습니다. 이것이 "구조화된 프로세스"의 가치입니다.

---

## 4. Kiro = AI-DLC의 제품화

Kiro의 핵심 기능들은 AI-DLC의 각 요소를 제품으로 구현한 것입니다. 이 대응 관계가 이 과정 전체의 뼈대입니다.

| AI-DLC 요소            | Kiro 기능             | 설명                                                    | 자세히                          |
| ---------------------- | --------------------- | ------------------------------------------------------- | ------------------------------- |
| 스티어링 파일          | **Steering**    | `.kiro/steering/`에 규칙을 두면 그 규칙대로 코드 생성 | [04장](./04-부가기능.md)         |
| 구조화된 개발 프로세스 | **Specs (SDD)** | 요구사항 → 설계 → 작업을 자동 생성하고 사람이 승인    | [03장](./03-sdd-명세주도개발.md) |
| 자동 체크포인트        | **Hooks**       | 파일 저장·변경 시 린트/테스트 등을 자동 실행           | [04장](./04-부가기능.md)         |

정리하면, **Steering은 일관성을 위해**, **Specs는 구조화된 프로세스를 위해**, **Hooks는 출력물의 자동 검증을 위해** 존재합니다. 모두 "AI에게 좋은 개발 프로세스를 강제한다"는 하나의 철학에서 나왔습니다.

---

## 5. 언제 AI-DLC, 언제 바이브 코딩?

AI-DLC가 항상 정답은 아닙니다. 상황에 맞게 고르는 것이 중요합니다.

| 상황                                   | 추천                         |
| -------------------------------------- | ---------------------------- |
| 양질의 코드                            | **AI-DLC (Kiro Spec)** |
| 빠르게 보여줄 프로토타입               | 바이브 코딩                  |
| 일회성/버리는 스크립트(데이터 변환 등) | 바이브 코딩                  |
| 팀이 함께 유지보수할 코드              | **AI-DLC (Kiro Spec)** |

간단한 기준: **"양질의 코드"는 AI-DLC, "그냥 돌려볼 코드"는 바이브 코딩.**

---

## 정리

- **DLC = 개발 생명주기**, **AI-DLC = AI가 사람과 같은 개발 프로세스를 따르게 강제하는 틀**이다.
- AI-DLC는 요구사항 → 설계 → 구현 → 테스트 → 리뷰 → 배포 단계로 나뉘고, **단계마다 사람이 검증**한다.
- Kiro의 Steering/Specs/Hooks는 각각 AI-DLC의 스티어링·구조화 프로세스·자동 체크포인트를 제품화한 것이다.
