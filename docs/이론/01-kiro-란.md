# 01. Kiro란?

> **이 챕터의 목표**
>
> - Kiro가 무엇인지 한 문장으로 설명할 수 있다.
> - 일반적인 AI 코딩 도구와 Kiro의 차이를 이해한다.
> - "바이브 코딩"의 한계와 Kiro가 해결하려는 문제를 안다.

---

## 1. 한 줄 정의

**Kiro는 AWS가 만든 AI 기반 개발 환경(Agentic IDE)으로, 프롬프트를 구조화된 요구사항·설계·구현 작업으로 바꿔 AI가 실행하도록 하는 도구입니다.**

VS Code 기반으로 동작하며, 단순히 코드를 자동완성해 주는 것을 넘어 "무엇을, 어떻게 만들지"를 먼저 정리한 뒤 구현에 들어가는 것이 특징입니다.

---

## 2. 왜 Kiro가 등장했나: 바이브 코딩의 한계

2025년 즈음부터 "바이브 코딩(Vibe Coding)"이라는 말이 유행했습니다. "이런 앱 만들어줘" 하고 AI에게 던지면 나온 코드를 그대로 쓰는 개발 방식입니다.

### 자주 겪는 상황: "A를 원했는데 B가 나온다"

바이브 코딩을 하다 보면 **내가 원한 것과 AI가 만든 것이 어긋나는** 경험을 반복하게 됩니다. 요구가 두루뭉술할수록, AI는 그럴듯하지만 내 의도와 다른 결과를 내놓습니다.

```text
나:  "직원 목록 조회 기능 만들어줘"
AI:  (전체 직원을 한 번에 반환하는 API를 생성)

나:  "아니, 그거 말고 부서별로 묶어서 페이징되게 해줘"      ← 다시 설명
AI:  (부서별 그룹핑 추가. 그런데 페이징은 프런트에서 자르는 방식)

나:  "페이징은 서버에서 처리해야 해. 그리고 퇴사자는 빼줘"   ← 또 다시 설명
AI:  (서버 페이징 적용. 그런데 응답 포맷이 기존 API와 다름)

나:  "응답 포맷은 기존 UpdateResponse 패턴에 맞춰줘"        ← 또또 다시 설명
...
```

문제는 **A를 요구했는데 B가 나오고, 검토 후 "이거 아니야, A야"라고 다시 입력하는 왕복이 계속된다**는 점입니다. 이 왕복이 쌓이면 처음부터 설계를 적어두는 것보다 오히려 느려지고, 맥락이 길어질수록 AI가 앞의 요구를 잊어버리기도 합니다.

바이브 코딩에서 이런 재작업이 반복되는 전형적인 패턴을 정리하면 다음과 같습니다.

| 내가 요구한 것(A) | AI가 만든 것(B)        | 왜 어긋났나                    | 결과      |
| ----------------- | ---------------------- | ------------------------------ | --------- |
| "직원 목록 조회"  | 전체를 한 번에 반환    | 페이징·필터 요구를 명시 안 함 | 다시 요청 |
| "부서별 페이징"   | 프런트에서 자르는 방식 | "서버 페이징"이라고 안 함      | 다시 요청 |
| "퇴사자 제외"     | 상태 필터 누락         | 상태 조건을 빠뜨림             | 다시 요청 |
| "응답 포맷 통일"  | 제각각 포맷            | 프로젝트 규칙을 모름           | 다시 요청 |

이렇게 **요구 → 어긋난 결과 → 재설명**의 왕복이 반복되는 것이 바이브 코딩의 가장 흔한 비용입니다. 그 밖에도 다음과 같은 문제가 함께 따라옵니다.

| 문제        | 설명                                                                                           |
| ----------- | ---------------------------------------------------------------------------------------------- |
| 설계 부재   | AI는 "동작하는 코드"는 잘 쓰지만 "좋은 설계"는 고려하지 않는다. 확장성·유지보수성이 희생된다. |
| 테스트 부재 | 생성된 코드에 테스트가 없어 버그가 숨어 있어도 알기 어렵다.                                    |
| 보안 취약   | API 키 하드코딩, SQL 인젝션 미대응 같은 기본 보안이 누락되기 쉽다.                             |
| 일관성 부재 | 같은 프로젝트 안에서도 코딩 스타일이 제각각이 된다.                                            |

결과적으로 **"돌아가긴 하는데 완성도가 낮은 코드"** 가 양산됩니다. 이것이 바이브 코딩의 한계입니다.

> 💡 바이브 코딩이 나쁜 것은 아닙니다. 프로토타입이나 일회성 스크립트에는 여전히 효율적입니다. 다만 **양질의 코드**에는 다른 접근이 필요합니다.

## 3. Kiro는 무엇이 다른가

일반적인 AI 코딩 도구(자동완성형 어시스턴트)와 Kiro를 비교하면 다음과 같습니다.

| 항목        | 일반 AI 코딩 도구          | Kiro                                         |
| ----------- | -------------------------- | -------------------------------------------- |
| 접근 방식   | 프롬프트 → 즉시 코드 생성 | 프롬프트 → 요구사항 → 설계 → 작업 → 구현 |
| 사람의 역할 | 결과 코드 확인             | 각 단계 검토·승인                           |
| 산출물      | 코드 조각                  | 명세 문서 + 설계 + 추적 가능한 작업 + 코드   |
| 일관성      | 세션마다 달라짐            | 규칙(Steering)으로 프로젝트 전체 일관 유지   |
| 자동화      | 수동 반복                  | 이벤트 기반 자동화(Hooks)                    |

핵심은 Kiro가 "경험 많은 시니어 엔지니어처럼 동작한다"는 점입니다. 맥락을 분석하고, 기술 명세를 작성하고, 설계 계약을 세우고, 작업을 잘게 쪼갠 뒤 구현합니다. 그리고 사람이 중간중간 검토해 의도와 일치하는지 확인합니다.

---

## 4. Kiro의 두 가지 작업 방식

Kiro는 상황에 따라 두 가지 세션 방식을 제공합니다.

- **Vibe 세션**: 대화형으로 빠르게 질문하고 탐색적으로 코딩할 때. 프로토타이핑에 적합.
- **Spec 세션**: 요구사항 → 설계 → 작업으로 이어지는 구조화된 워크플로우. 양질의 코드에 적합. (→ [03장 SDD](./03-sdd-명세주도개발.md)에서 자세히)

두 방식 모두에서 **자율성 모드**를 선택할 수 있습니다.

- **Autopilot(기본)**: Kiro가 작업을 끝까지 자율 수행. 변경 사항을 언제든 확인·되돌리기 가능.
- **Supervised**: 변경이 생길 때마다 승인을 받고, 변경 단위로 수락/거부 가능.

## 5. Kiro를 떠받치는 네 가지 축

이후 챕터에서 하나씩 다룰 핵심 요소입니다. 지금은 "이런 게 있구나" 정도로만 봐 두세요.

```
Kiro
├── 철학:   AI-DLC        → AI에게 좋은 개발 프로세스를 강제한다      (02장)
├── 실천:   SDD / Specs   → 요구사항·설계·작업을 구조화해 개발한다    (03장)
└── 도구:   부가 기능       → Steering · Agent · Skills · Hooks · MCP  (04장)
```

---

## 정리

- Kiro는 AWS가 만든 **에이전트형 AI IDE**로, 코드를 바로 뽑는 대신 명세와 설계를 먼저 세운다.
- 바이브 코딩의 한계(설계·테스트·보안·일관성 부재)를 극복하기 위해 등장했다.
- 사람이 각 단계를 검토·승인하므로 **높은 품질의 코드**를 만들 수 있다.
