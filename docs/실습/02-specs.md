# 실습 ②. Specs — 요구사항·설계 및 구현

> **과정**: 기본
> **소요 시간**: 약 40분
> **난이도**: ★★★☆☆
> **실습 목표**: 기존 HR API를 활용하는 React 관리자 화면을 **명세 주도(Spec)**로 설계·구현하는 흐름을 익힌다. 이 저장소에는 **완성된 예시 Spec과 프론트엔드가 이미 있으므로**, 그 결과물을 되짚으며 Spec 워크플로를 체득한다.

---

## 0. 이 실습에서 배우는 것

- Spec 워크플로: **요구사항(requirements) → 설계(design) → 작업(tasks) → 구현**의 단계별 승인 흐름
- 수용 기준(acceptance criteria)을 WHEN/THEN 형태로 쓰는 법
- 승인된 Spec을 바탕으로 코드를 점진적으로 구현하고 추적하는 법

> 💡 **왜 Spec인가**: "대충 말로 시키고 바로 코딩"하면 설계 합의가 빠져 재작업이 큽니다. Spec은 **구현 전에 요구사항·설계를 문서로 합의**하고, 그 문서에 맞춰 작업을 쪼개 구현합니다. 큰 기능일수록 효과가 큽니다.

---

## 1. Spec이란

Spec은 하나의 기능을 3개 문서로 정의합니다. 위치는 `.kiro/specs/<기능명>/`.

| 파일 | 내용 | 승인 포인트 |
|------|------|-------------|
| `requirements.md` | 사용자 스토리 + 수용 기준(WHEN/THEN) | 요구사항 합의 |
| `design.md` | 화면 구성, 컴포넌트/모듈 구조, API 연동, 타입 매핑 | 설계 합의 |
| `tasks.md` | 구현 작업 목록(체크박스) | 작업 단위로 구현·검증 |

각 단계는 **승인 후 다음으로** 넘어갑니다. 구현은 `tasks.md`의 항목을 하나씩 처리합니다.

---

## 2. 이미 있는 예시 Spec 살펴보기

이 저장소에는 프론트엔드 Spec이 **이미 완성되어 있습니다.**

```text
.kiro/specs/hr-web-frontend/
├── requirements.md   # 4개 도메인(부서/직원/출퇴근/휴가) 요구사항
├── design.md         # 컴포넌트·API 연동 설계
└── tasks.md          # 구현 작업 목록
```

Kiro로 열어 구조를 파악해 봅니다.

```text
.kiro/specs/hr-web-frontend/requirements.md 를 읽고,
어떤 요구사항이 어떤 수용 기준으로 정의됐는지 도메인별로 요약해줘.
```

실제 `requirements.md`의 수용 기준은 아래처럼 **구체적인 API까지 명시**되어 있습니다 (발췌):

> 요구사항 3 (직원 관리) — "WHEN 직원 페이지에 진입하면 THEN 시스템은 `GET /v1/employees`로 직원 목록을 부서명과 함께 표시해야 한다."

> 💡 **실무 팁 — 수용 기준에 API/필드를 박아라**: "직원 목록을 보여준다"가 아니라 "`GET /v1/employees`로 부서명 포함 표시"처럼 **검증 가능한 형태**로 써야, 구현과 검증이 명확해집니다.

---

## 3. 설계 문서 이해하기 (design)

```text
.kiro/specs/hr-web-frontend/design.md 를 읽고,
컴포넌트 구조와 API 연동 방식(axios 클라이언트, TanStack Query 훅, 타입)을 요약해줘.
```

이 설계가 실제 코드로 어떻게 떨어졌는지 대조해 봅니다:

| 설계 요소 | 실제 구현 위치 |
|-----------|----------------|
| axios 클라이언트 + 에러 정규화 | `frontend/src/api/client.ts` |
| 도메인별 API 함수 | `frontend/src/api/{employees,departments,attendances,leaves}.ts` |
| 서버 상태 훅 | `frontend/src/hooks/use*.ts` (TanStack Query) |
| 백엔드 DTO 대응 타입 | `frontend/src/types/api.ts` |
| 공통 UI | `frontend/src/components/common/` (DataTable, Modal 등) |

> 💡 CORS는 실습 ①에서 본 규칙대로, Vite dev 서버가 `/v1/*`를 `http://localhost:8080`으로 프록시합니다. 별도 CORS 설정이 없습니다.

## 4. 직접 해보기 — 작은 Spec 만들기

예시를 읽었으니, 이번엔 **작은 기능 하나를 새 Spec으로** 만들어 봅니다. 예: "대시보드에 부서별 인원 요약 카드 추가".

Kiro 채팅에 입력:

```text
Spec을 새로 만들어줘: "대시보드 부서별 인원 요약".
- 요구사항: 대시보드 상단에 부서별 직원 수를 카드로 표시한다.
  데이터는 GET /v1/employees 응답을 departmentName 기준으로 집계한다.
  (백엔드 수정 없이 프론트에서 집계)
- 기존 hr-web-frontend Spec의 문서 형식과 컨벤션을 따라줘.
먼저 requirements.md 초안부터 보여주고, 내 승인 후 design.md로 넘어가.
```

그 뒤 **단계별로 승인**하며 진행합니다: requirements 확인 → design 확인 → tasks 생성 → 구현.

### 대조용 완성 예시

위 프롬프트와 같은 주제로 만든 Spec이 `.kiro/specs/dashboard-department-summary/`에 있습니다. **직접 만든 결과와 비교**하는 용도입니다. 이 예시는 requirements/design/tasks **문서까지만** 있고, 코드는 구현하지 않은 상태입니다.

| 확인할 부분 | 어디를 보나 | 볼 포인트 |
|-------------|-------------|-----------|
| 범위 | `requirements.md` "범위 밖" | 백엔드·신규 라이브러리·차트·클릭 이동을 **하지 않는 것**으로 명시 |
| 수용 기준 | `requirements.md` Requirement 1~3 | 정상 흐름뿐 아니라 로딩·오류·빈 상태(`IF … THEN`)와 비회귀 기준 포함 |
| 가정 | `requirements.md` "미결 사항 / 가정" | 퇴사자 포함 여부, 0명 부서 표시 여부 등 **승인 전에 확인할 질문과 기본 가정**을 표로 정리 |
| 추적성 | `tasks.md`의 `_Requirements: …_` | 모든 task가 요구사항 번호와 연결됨 |
| 검증 | `tasks.md` 4번, 5번 | 정적 검증(`typecheck`/`build`, 백엔드 무변경 확인)과 사용자 수동 검증을 분리 |

> 💡 **"가정 표"가 승인 단계의 핵심**: 위 예시는 "직원이 0명인 부서도 보일까?" 같은 판단을 AI가 임의로 정하지 않고 **질문으로 드러내 승인받는 구조**입니다. 직접 만든 Spec에도 같은 표가 있는지 확인해 보세요.

> ⚠️ **한 번에 다 시키지 마라**: "요구사항부터 구현까지 알아서 다 해줘"라고 하면 설계 합의가 빠집니다. 각 단계를 **읽고 승인**한 뒤 다음으로 넘어가는 것이 Spec의 핵심 가치입니다.

## 5. 실행 및 확인

```bash
cd frontend
npm install          # 처음 한 번
npm run dev          # http://localhost:5173
```

- [ ] 직원 목록이 부서명과 함께 렌더링된다

## 6. 실무 가이드 — Spec 작성 시 유의사항·체크사항·꿀팁

여기부터는 실습을 넘어 **실무 과제에 바로 적용**할 때의 기준입니다. 예시는 이 저장소의 `hr-web-frontend` Spec에서 가져왔습니다.

### 6-1. 작성 전에 확인할 것 (착수 체크)

- [ ] 기능이 **하나의 목적**으로 설명되는가? (여러 기능이 섞이면 Spec을 나눈다)
- [ ] 데이터 소스(API)와 **실제 응답 필드**를 코드/Swagger로 확인했는가? (추측 금지)
- [ ] **범위 밖(하지 않을 것)**을 정했는가? 예: "백엔드 수정 없음", "신규 라이브러리 추가 없음"
- [ ] 따라야 할 Steering(보안·아키텍처·엔지니어링 규칙)을 확인했는가?
- [ ] 비슷한 기존 Spec/코드가 있는가? 있으면 **형식과 패턴을 그대로 따르게** 지시했는가?

### 6-2. 유의사항 (자주 틀리는 지점)

| 구분 | 유의사항 | 이 저장소의 근거/예시 |
|------|----------|----------------------|
| 범위 | **작게 쪼갠다.** 한 Spec은 한 기능, 한 번에 검토 가능한 크기 | 실습용 "부서별 인원 요약 카드"는 화면 1개·API 0개 추가 |
| 요구사항 | 수용 기준은 **WHEN/THEN + 검증 가능한 값**(API 경로, 필드, 상태)으로 쓴다 | `WHEN 직원 페이지에 진입하면 THEN GET /v1/employees로…` |
| 요구사항 | 정상 흐름만 쓰지 말고 **IF 예외 조건**(빈 값, 실패, 권한)을 같이 쓴다 | `IF 이름이 비어 있으면 THEN 제출을 막고 검증 메시지 표시` |
| 설계 | 백엔드 **계약 불일치**(필드명 차이 등)는 설계/타입 주석에 남긴다 | tasks 2번: "requestDate/필드명 불일치 등 계약 주석 반영" |
| 설계 | **가정과 미결 사항**을 문서 끝에 명시한다 | design.md "미결 사항 / 가정" 섹션 |
| 설계 | 버전·수치 같은 **외부 사실은 확인 날짜**를 같이 적는다 | design.md "…2026-10-23 기준으로 확인한 값" |
| 작업 | 각 task에 **요구사항 번호를 연결**해 추적성을 확보한다 | `_Requirements: 2.1, 2.2_` |
| 작업 | task는 **한 번에 구현·검증·커밋 가능한 크기**로 쪼갠다 | 4.1~4.4처럼 도메인별로 분할 |
| 진행 | 검증하지 못한 task는 **완료로 표시하지 않는다**. 이유를 남긴다 | tasks 13번 `[~]` "보류: Node/npm 미설치" |
| 변경 | 요구사항이 바뀌면 **requirements → design → tasks 순서로** 동기화한다 | 코드만 고치면 문서와 어긋난다 |
| 보안 | Spec에 **비밀번호·토큰·운영 DB 접속 정보**를 쓰지 않는다 | 보안 규칙: 값 노출 금지, 키 이름/위치만 기록 |

> ⚠️ **승인 없이 구현으로 넘어가지 마라**: 이 프로젝트의 규칙은 구현 전 명시적 승인을 요구합니다. requirements → design → tasks 각 단계에서 "승인" 또는 수정 요청을 분명히 남기세요.

> ⚠️ **"완료"를 문서로만 주장하지 마라**: 타입 체크/빌드/테스트를 **실제로 실행한 뒤에만** task를 완료 처리합니다. 실행하지 못했다면 못 했다고 적습니다.

### 6-3. 단계별 승인 체크리스트 (리뷰어용)

**requirements.md 승인 전**
- [ ] 사용자 스토리가 "누가 / 무엇을 / 왜"를 담고 있다
- [ ] 모든 수용 기준이 WHEN/THEN(또는 IF/THEN) 형식이고 **테스트로 확인 가능**하다
- [ ] 예외·빈 상태·오류 케이스가 최소 1개씩 있다
- [ ] 범위 밖 항목이 명시되어 있다

**design.md 승인 전**
- [ ] 모든 요구사항이 설계의 어느 부분에서 충족되는지 **번호로 연결**된다 (예: `(Req 2.6)`)
- [ ] 기존 구조(레이어·폴더·네이밍)를 따르고, **새 프레임워크/라이브러리를 임의로 추가하지 않는다**
- [ ] 실제 API 응답 필드와 타입 매핑이 맞다
- [ ] 오류 처리, 로딩/빈 상태 처리 방식이 정해져 있다
- [ ] 가정·미결 사항이 적혀 있다

**tasks.md 승인 전**
- [ ] 의존 순서가 맞다 (타입 → API → 훅 → 컴포넌트 → 페이지)
- [ ] 각 task에 `_Requirements: n.n_` 연결이 있다
- [ ] 마지막에 **빌드/타입 체크 검증 task**가 있다
- [ ] 한 task가 너무 크지 않다 (한 번에 리뷰·커밋 가능)

**구현 후 (완료 처리 전)**
- [ ] `npm run typecheck` 통과
- [ ] `npm run build` 통과
- [ ] 수용 기준을 화면/응답에서 **실제로 하나씩 확인**했다
- [ ] 범위 밖으로 지정한 파일(예: 백엔드)을 건드리지 않았다 (`git status`로 확인)
- [ ] tasks.md의 체크 상태가 실제 진행과 일치한다

### 6-4. 꿀팁

> 💡 **프롬프트 템플릿**: 아래 틀을 채우면 처음부터 품질이 올라갑니다.
>
> ```text
> Spec을 만들어줘: "<기능명>"
> - 목적: <한 문장>
> - 데이터 소스: <API 경로> (응답 필드는 코드를 읽고 확인해줘)
> - 범위 밖: <하지 않을 것>
> - 참고: .kiro/specs/hr-web-frontend 의 형식과 컨벤션을 따라줘
> 먼저 requirements.md 초안만 보여주고, 내 승인 후 design.md로 넘어가.
> 가정한 부분은 따로 목록으로 알려줘.
> ```

> 💡 **"가정 목록"을 먼저 달라고 하라**: AI는 모르는 부분을 그럴듯하게 채우기 쉽습니다. "가정한 것과 확인하지 못한 것을 구분해서 알려줘"라고 요청하면 틀린 가정을 승인 단계에서 잡을 수 있습니다.

> 💡 **기존 코드/Spec을 본보기로 지정하라**: "hr-web-frontend Spec처럼", "`frontend/src/api/employees.ts` 패턴대로"처럼 파일을 지정하면 스타일이 일관되고 재작업이 줄어듭니다. 채팅에서 `#File`로 파일을 붙이면 더 정확합니다.

> 💡 **task는 하나씩 실행시켜라**: "tasks 전부 구현해줘"보다 "task 4.1만 구현해줘"가 리뷰와 롤백이 쉽습니다. task 하나가 끝나면 타입 체크 → 커밋 순으로 끊으세요.

> 💡 **막히면 코드보다 Spec을 고쳐라**: 구현 중 요구사항·설계가 틀렸다는 걸 알게 되면, 코드를 땜질하지 말고 Spec을 먼저 수정해 합의한 뒤 다시 진행합니다. 문서가 항상 현재 코드의 설명서여야 합니다.

> 💡 **Spec이 필요 없는 경우도 있다**: 오타 수정, 단일 파일의 작은 변경은 Spec 없이 바로 요청하는 편이 빠릅니다. 여러 파일·여러 화면에 걸치거나 합의가 필요한 기능에 Spec을 쓰세요.

> 💡 **커밋 단위를 Spec과 맞춰라**: `feat: task 4.1 departments API`처럼 task 번호를 커밋 메시지에 넣으면 나중에 요구사항 → task → 커밋을 따라가기 쉽습니다. 문서(`.kiro/specs/`)와 코드는 가능하면 같은 PR에 담으세요.

> 💡 **리뷰는 문서 단계에서**: 코드 리뷰보다 requirements/design 리뷰가 비용이 훨씬 쌉니다. 팀 리뷰가 필요하면 구현 전에 Spec 문서만 먼저 PR로 올려 합의하세요.

## 7. 완료 체크리스트

## 8. 흔한 에러 & 해결

| 증상 | 원인 | 해결 |
|------|------|------|
| 화면은 뜨는데 데이터가 비어 있음 | 백엔드 미기동 또는 데이터 미적재 | 실습 ⓪ 절차로 백엔드·데이터 확인 |
| `Network Error` / 404 | Vite 프록시 대상 불일치 | 백엔드가 `http://localhost:8080`인지, `.env`의 `VITE_PROXY_TARGET` 확인 |
| 타입 에러 | `types/api.ts`와 백엔드 응답 불일치 | 실제 응답 필드와 타입을 대조 |
