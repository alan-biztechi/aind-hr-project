## 1. 이 저장소의 `.kiro/` 구성 (재사용 가능한 자산)

실습에서 쓴 것들은 전부 `.kiro/` 아래에 있습니다.

```text
.kiro/
├── steering/          # 공통 규칙 (실습 ①)
│   ├── engineering-rules.md     # 스택/빌드·테스트/코딩 규율
│   ├── architecture-rules.md    # 아키텍처 리뷰 기준·심각도 정의
│   └── security-rules.md        # 보안 규칙 (우선순위 최상위)
├── specs/             # 기능 명세 (실습 ②)
│   ├── hr-web-frontend/             # requirements/design/tasks 완성 예시
│   └── dashboard-department-summary/ # 작은 Spec 예시 (문서만, 구현 없음)
├── agents/            # 커스텀 에이전트와 리뷰 오케스트레이션 (실습 ③)
│   ├── code-reviewer.json       # 실습 ③에서 직접 고쳐 봄 (단일 리뷰어)
│   ├── sa-orchestrator.json     # 메인(조율자)
│   ├── architecture-reviewer.json
│   ├── infra-reviewer.json
│   ├── api-reviewer.json
│   ├── db-reviewer.json
│   ├── risk-aggregator.json
├── docs/              # 검증 가이드·스크립트
│   ├── TESTING.md               # 오케스트레이터 검증 + 정답지
│   └── validate_agents.py       # 에이전트 정적 검증
└── hooks/             # 자동화 (실습 ⑤에서 생성)
```

> 💡 `docs/실습/`(이 문서들)은 **실습 교재**이고, `.kiro/`는 **실제로 Kiro가 읽는 설정**입니다. 둘을 혼동하지 마세요.

> 💡 `.kiro/agents/`에는 **에이전트 정의 파일**(JSON, 또는 frontmatter가 있는 Markdown)만 둡니다. 설명 문서는 `.kiro/docs/`로 옮기세요.

## 2. 내 프로젝트에 적용하기

### 2-1. Steering부터 (가장 쉬움, 효과 큼)

1. 내 프로젝트에 `.kiro/steering/` 폴더를 만든다.
2. `engineering-rules.md`를 복사해 **내 스택으로 교체**한다 (언어/프레임워크/빌드·테스트 명령).
3. `security-rules.md`는 거의 그대로 재사용 가능 — "프로덕션" 정의와 파괴적 명령 통제는 범용적이다.
4. 규칙이 많으면 범위 좁은 것은 `inclusion: fileMatch`로 건다.

### 2-2. 리뷰 오케스트레이터 이식 (실습 ③)

1. `.kiro/agents/`의 JSON 6개 파일(`sa-orchestrator` + 서브에이전트 5개)을 복사한다.
2. 각 리뷰어 프롬프트의 **"기술 전제"만** 내 스택에 맞게 바꾼다. (이 저장소는 MyBatis/MySQL 기준 — JPA/PostgreSQL 등이면 그 부분만 수정)
3. `.kiro/docs/validate_agents.py`로 정적 검증: `python3 .kiro/docs/validate_agents.py`
4. **정답지(Expected Findings)를 내 코드 기준으로 새로 작성**한다. (`TESTING.md` 형식 참고) — 정답지 없는 리뷰는 신뢰하기 어렵다.

### 2-3. Hook 자동화 (실습 ⑤)

- `lint-on-save.json`의 `matcher`(대상 경로)와 `command`(lint 명령)만 내 프로젝트 것으로 바꾼다. 예: 백엔드면 `src/.*\.java$` + 포맷터 명령.
- 훅 환경에서 빌드 도구(npm, mvn 등)가 보이는지 먼저 확인한다 ([실습 ⑤ 2절](./05-hooks.md)).
- (선택) `pr-workflow.md`를 만들었다면 빌드 명령과 기준 브랜치(`main`)를 내 프로젝트에 맞게 바꾼다.
- 프로젝트 규칙 중 린터로 표현할 수 있는 것은 린터 설정으로 옮긴다. 그러면 lint-on-save 훅이 그 규칙까지 자동으로 잡는다.

**많이 쓰는 다른 훅 사례** (필요할 때 하나씩 추가)

| 사례 | 트리거 / matcher | 액션 |
|------|------------------|------|
| 민감 파일 수정 막기 | `PreToolUse` / `write` | agent: "대상이 `application*.yml`, `.env`이면 수정하지 말고 먼저 물어봐" |
| Spec 작업 완료 후 검증 | `PostTaskExec` | agent: "`frontend`에서 `npm run typecheck`를 실행하고 결과를 보고해" |
| 시크릿 스캔 | `Stop` | agent: 변경 파일의 키·토큰·비밀번호 점검 (매 턴 실행이라 무거움) |
| 세션 시작 맥락 | `SessionStart` | command: `git status --short` (stdout이 맥락에 추가됨) |

> 💡 훅은 이벤트마다 실행되므로 **빈도**를 먼저 생각하세요. `Stop`·`PreToolUse`처럼 자주 발생하는 트리거에 `agent` 액션을 걸면 매번 AI가 호출됩니다.

> ⚠️ **보안 규칙은 먼저 이식하라**: 비밀정보 하드코딩 금지, 공유 DB 직접 변경 금지, 파괴적 명령 승인 같은 규칙은 다른 어떤 규칙보다 먼저 깔아두는 것이 안전합니다.

## 5. 사용량(크레딧) 아끼는 법

> **한 줄 요약**: 사용량은 **① 대화가 얼마나 길어졌는지 × ② 매번 따라붙는 규칙이 얼마나 많은지 × ③ 어떤 모델을 쓰는지**로 정해집니다. 이 셋을 줄이면 됩니다.
>
> 출처: Kiro 공식 문서 (Billing · Models · Steering · Skills · Compaction · MCP Tool Search). 하단에 링크가 있습니다.

### 먼저 이것만 — 효과 큰 순서 TOP 7

| 순위 | 습관 | 어떻게 | 자세히 |
|:---:|------|--------|:------:|
| 1 | **작업이 바뀌면 새 대화** | 이전 대화는 매 요청마다 같이 전송됩니다 | 5-2 |
| 2 | **파일·범위를 지정해서 요청** | `#파일경로`로 읽을 곳을 좁혀 줍니다 | 5-2 |
| 3 | **Steering은 `always`를 최소로** | 나머지는 `fileMatch` / `auto` / `manual`로 | 5-3 |
| 4 | **기본 모델은 Auto** | 막힐 때만 상위 모델, 끝나면 되돌리기 | 5-4 |
| 5 | **작은 수정은 Spec 대신 일반 대화** | Spec은 단계마다 AI를 호출합니다 | 5-5 |
| 6 | **반복 검증은 `command` Hook** | 린트·포맷은 AI 호출 없이 실행됩니다 | 5-5 |
| 7 | **검증은 명령으로** | `curl`, `grep`, `./mvnw test`는 AI를 쓰지 않습니다 | 5-5 |

### 5-1. 사용량은 이렇게 계산됩니다

- **크레딧 방식**: 요청마다 **소수 단위로 차감**됩니다. 짧은 프롬프트·간단한 수정은 적게, 길고 복잡한 작업은 많이 씁니다.
- **플랜별 월 크레딧** (매월 갱신)

| 플랜 | Free | Pro | Pro+ | Pro Max | Power |
|------|:---:|:---:|:---:|:---:|:---:|
| 월 크레딧 | 50 | 1,000 | 2,000 | 5,000 | 10,000 |

- **대화가 길수록 비쌉니다.** 새 메시지를 보낼 때마다 앞선 대화·규칙·읽은 파일이 함께 전송되기 때문입니다.

> 💡 **"한 번에 크게"보다 "작게 나눠서, 범위를 좁혀서"** 요청하는 쪽이 유리합니다.

### 5-2. 대화 관리

**이렇게 하세요**

| 하세요 ✅ | 하지 마세요 ❌ |
|-----------|---------------|
| 작업이 바뀌면 **새 대화**를 시작 | 하루 종일 한 대화에서 이어가기 |
| `#frontend/src/api/employees.ts`처럼 **파일을 지정** | "프로젝트 전체를 보고 알아서 해줘" |
| 빌드·테스트 로그는 **필요한 부분만** 보기 | 긴 로그 전체를 그대로 대화에 쌓기 |
| 채팅 패널의 **컨텍스트 사용량 미터**를 가끔 확인 | 한도에 닿을 때까지 모르고 진행 |

**Compaction(자동 요약)이란?**

대화가 모델의 컨텍스트 한도에 가까워지면 Kiro가 **오래된 대화를 요약으로 바꾸고**, 최근 대화는 그대로 둡니다.

| 항상 보존됨 | 압축될 수 있음 |
|-------------|----------------|
| 작업 상태(완료/진행/예정) | 도구 호출 상세 |
| 수정한 파일 경로 | 중간 추론 과정 |
| 핵심 결정과 제약 | 이전 메시지의 코드 조각 |
| 다음 할 일, 내가 말한 요구사항 | 해결된 에러, 탐색용 대화 |

> ⚠️ **`/compact`는 IDE에서 쓸 수 없습니다.** 수동 `/compact`는 **CLI에서만** 지원되고, IDE는 자동 요약만 동작합니다. IDE에서는 **새 대화를 시작**하는 것이 가장 확실합니다.
>
> ⚠️ Compaction은 **되돌릴 수 없습니다.** 전체 기록이 필요하면 요약되기 전에 세션을 내보내세요.

### 5-3. Steering · Skill · MCP — "매번 따라붙는 것" 줄이기

Steering은 설정에 따라 **매 요청에 자동으로 실립니다.** 그래서 가장 흔한 낭비 원인입니다.

**① Steering 4가지 모드 — 언제 실리나?**

| 모드 | 언제 실리나 | 적합한 규칙 | 비용 |
|------|-------------|-------------|:----:|
| `always` (기본값) | **모든 요청에 항상** | 보안, 기술 스택, 코딩 기본 규칙 | 🔴 높음 |
| `fileMatch` | 패턴에 맞는 **파일을 다룰 때만** | 프론트 전용, 테스트 전용 규칙 | 🟡 중간 |
| `auto` | 내 **요청이 설명과 맞을 때만** | 특정 작업 절차, 참고 자료 | 🟢 낮음 |
| `manual` | `#이름` 또는 `/`로 **부를 때만** | 가끔 쓰는 가이드, 마이그레이션 | 🟢 가장 낮음 |

**② 어떤 모드로 할지 고르는 법**

```text
모든 작업에서 지켜야 하나?  ── 예 ──▶ always   (예: 보안 규칙)
        │ 아니오
        ▼
특정 파일 종류에만 해당하나? ── 예 ──▶ fileMatch (예: frontend/**/*.tsx)
        │ 아니오
        ▼
요청 내용으로 판단 가능한가? ── 예 ──▶ auto      (description을 구체적으로)
        │ 아니오
        ▼
                                   manual    (필요할 때 #이름으로 호출)
```

**③ 모드 설정 예시** (파일 맨 위 front matter)

```yaml
---
inclusion: fileMatch
fileMatchPattern: "frontend/**/*.tsx"
---
```

```yaml
---
inclusion: auto
name: api-design
description: REST API 설계 규칙. API 엔드포인트를 만들거나 수정할 때 사용.
---
```

**④ 함께 알아둘 것**

| 대상 | 알아둘 점 |
|------|-----------|
| `AGENTS.md` | inclusion 모드를 **지원하지 않고 항상 포함**됩니다. 길게 쓰지 마세요 |
| Steering 파일 | **한 파일에 한 도메인**, 짧게. 클수록 실릴 때마다 비용이 커집니다 |
| Skill | 시작 시 `name`·`description`만 읽고, **요청이 맞을 때만 전체를 로드**합니다. 반복 절차는 Skill로 분리하세요 |
| MCP 서버 | 쓰지 않는 서버는 끄세요. Tool Search(IDE 1.3 이상 자동)가 필요한 도구 정의만 불러와 부담을 줄여 줍니다 |
| 커스텀 에이전트 | Steering이 **자동 포함되지 않습니다.** `resources`에 지정한 것만 읽습니다 |

> 💡 `auto`와 Skill은 **description이 곧 호출 조건**입니다. 설명이 모호하면 필요할 때 안 실리거나, 불필요할 때 실립니다.

### 5-4. 모델과 추론 강도 선택

Kiro는 **Auto를 1.0x 기준**으로 모델별 상대 비용(배율)을 표시합니다. Auto로 10크레딧 드는 작업은 Opus 5.5(2.0x)에서는 약 20크레딧입니다.

| 모델 | 배율 | 이럴 때 |
|------|:---:|---------|
| **Auto** | 1.0x | **기본값.** 작업별로 품질과 비용을 균형 있게 선택 |
| Claude Opus 5.5 | 2.0x | 어려운 문제, 여러 파일에 걸친 긴 작업 |
| Claude Sonnet 5.5 | 1.3x | 범위가 정해진 코딩, 버그 수정, 리뷰 |
| Claude Haiku 5.5 | 0.06x | 빠른 응답이 필요한 대량 작업 (100K 토큰 이하) |
| Qwen3 Coder Next | 0.05x | 예산을 아끼며 긴 코딩 세션 |

> 📅 위 값은 **2026-11-12 기준** 공식 문서 내용입니다. 모델과 배율은 자주 바뀌니 [공식 Models 문서](https://kiro.dev/docs/models/)에서 최신 값을 확인하세요.

**실무 규칙 3가지**

1. **기본은 Auto.** 막힐 때만 상위 모델로 올리고, 끝나면 Auto로 되돌립니다. (모델 선택은 이후 모든 메시지에 적용됩니다)
2. **Effort(추론 강도)는 작업에 맞게.** 낮추면 응답이 빠르고 크레딧도 덜 듭니다. IDE의 모델 패널 Effort 슬라이더로 조절합니다.
   - 단순 수정·포맷 → 낮게 / 설계 검토·어려운 버그 → 높게
3. **긴 대화는 배율이 오를 수 있습니다.** GPT-5.6은 272K 토큰, Haiku 5.5는 100K 토큰을 넘으면 더 높은 배율이 적용됩니다.

---

### 5-5. 이 과정의 실습 기준 — 기능별 선택

| 상황 | 이렇게 | 이유 |
|------|--------|------|
| 작은 수정 | **일반 대화**로 진행 (Spec 쓰지 않기) | Spec(요구사항 → 설계 → 태스크)은 단계마다 AI를 호출 |
| 단순한 질문·수정 | 서브에이전트·리뷰 오케스트레이터 **쓰지 않기** | 에이전트마다 자기 컨텍스트를 따로 읽음 ([실습 ③](./03-sa-orchestrator.md)) |
| 린트·포맷 등 반복 검증 | **`command` 타입 Hook** | 모델을 호출하지 않음 ([실습 ⑤](./05-hooks.md)) |
| 자주 발동하는 이벤트 (저장, 매 턴) | `agent` 타입 Hook은 **피하기** | 발동할 때마다 AI가 호출됨 |
| 결과 확인 | `curl`, `grep`, `./mvnw test` 등 **명령으로 직접** | AI를 쓰지 않음 |

### 5-6. 사용량 확인과 관리

- **사용량 화면 확인**: Kiro 계정 설정에서 크레딧 소비를 볼 수 있습니다. 어떤 습관이 많이 쓰는지, 모델 선택이 소비에 얼마나 영향을 주는지 여기서 확인하는 것이 가장 정확합니다.
- **한도 알림**: 한도에 가까워지면 알림을 받을 수 있습니다. ([Managing usage notifications](https://kiro.dev/docs/billing/proactive-usage-notifications/))
- **크레딧이 부족하면**: 상위 플랜으로 올리거나 **추가(add-on) 크레딧**을 구매합니다. Free 플랜은 추가 구매가 불가능합니다.
