# AIND Kiro 실습 커리큘럼

Spring Boot + MyBatis 기반 HR 프로젝트를 소재로, Kiro의 핵심 기능을 **기본 → 실무 활용 → 심화** 순서로 익히는 실습 과정입니다. 실습 하나가 Kiro 기능 하나를 다룹니다.

> 처음 하는 분은 **반드시 [실습 ⓪ 시작하기](./00-시작하기.md)부터** 환경을 맞춘 뒤 ①~⑤를 차례로 따라가세요.

|------|------|------|-----------|-----------|------------|
| [00](./00-시작하기.md) | 기본 | 시작하기 | — | 저장소 준비 및 Spring Boot·MySQL 실행 확인 | 20분 |
| [01](./01-steering.md) | 기본 | Steering — 개발 표준 설정 | Steering | 기존 Backend 분석 및 개발 규칙 정의 | 25분 |
| [02](./02-specs.md) | 기본 | Specs — 요구사항·설계 및 구현 | Spec | 기존 HR API를 활용한 React 관리자 화면 개발 | 40분 |

## 과정 구성

- **기본 (00~02)**: 환경 준비 → Steering(공통 규칙) → Spec(명세 주도 개발)
- **핵심 (03)**: 커스텀 에이전트 직접 만들기 → 멀티에이전트 아키텍처 검토
- **실무 활용 (04~05)**: Skill로 버그 수정과 회귀 검증 → Hook 자동화
- **참고 (06)**: 실무 적용 가이드와 FAQ

## 대상 프로젝트

- **백엔드**: Spring Boot 3.2.5 + MyBatis + MySQL (HR/근태 관리) — 소스 `src/main/java/com/aind/hr/`, 매퍼 `src/main/resources/mapper/`
- **프론트엔드**: React 19 + TypeScript + Vite SPA — `frontend/` (이미 구현되어 있으며, 실습 ②에서 이 결과물을 Spec으로 되짚어 봅니다)

## 처음 시작하는 분을 위한 안내

- 각 문서는 **목표 → 개념 → 따라 하기(복붙 가능한 명령/프롬프트) → 검증 → 체크리스트 → 흔한 에러** 순서로 구성됩니다.
- 코드 블록은 **그대로 복사해서 실행**할 수 있도록 작성했습니다. 실행 전 "어디서 실행하는지"(프로젝트 루트 / `frontend/` / Kiro 채팅)를 먼저 확인하세요.
- `> 💡` 는 실무 팁, `> ⚠️` 는 자주 틀리는 함정입니다.

## 공통 — "Kiro에 입력"이 무슨 뜻인가 (한 번만 읽어두기)

실습 문서에 "**Kiro 채팅에 입력**"이라고 나오면 아래를 뜻합니다. 실행 위치는 세 종류뿐입니다.

| 표기 | 어디서 실행하나 |
|------|-----------------|
| **Kiro 채팅에 입력** | Kiro의 채팅 입력창에 프롬프트를 붙여넣고 보냅니다 (IDE 우측 채팅 패널 또는 `kiro-cli chat --v3`) |
| **터미널 / 프로젝트 루트에서** | 운영체제 터미널에서 `aind-hr-project` 폴더 기준으로 실행 |
| **`frontend/`에서** | 터미널에서 `cd frontend` 후 실행 |

**채팅에 파일을 넣을 때** `#파일경로`를 쓰면 그 파일이 대화 컨텍스트에 포함됩니다. 예: `#frontend/src/api/employees.ts`.

**에이전트 전환** (실습 ③부터 필요):
- IDE: 채팅 입력창 하단의 에이전트 드롭다운 → 원하는 에이전트 선택
- CLI: `kiro-cli chat --v3 --agent <이름>` (예: `--agent sa-orchestrator`). 이 저장소의 에이전트는 V3 전용이라 `--v3`가 필요합니다.

> 💡 ③을 뺀 나머지 실습은 기본(Default) 에이전트로 진행합니다. 에이전트 전환은 ③에서만 다룹니다.

## 사용량을 아끼는 법

- **실습마다 새 대화로 시작하세요.** 앞 실습의 대화가 이어지면 매 요청마다 그 내용이 함께 전송됩니다.
- 프롬프트에 **파일이나 범위를 지정**하세요. 읽는 양이 줄어듭니다.
- 검증은 가능한 한 `curl`, `grep` 같은 **명령으로** 하세요. AI를 쓰지 않습니다.
- ③ SA Orchestrator는 기본이 샘플 리포트 읽기(AI 0회)입니다. 직접 실행은 선택이며, 범위를 좁혀 요청하세요.
- **대화가 길어지면 `/compact`로 요약하세요.** 이전 내용이 요약되어 컨텍스트가 줄어듭니다.
- **Steering은 항상 필요한 것만 `inclusion: always`(기본값)로 두세요.** always 파일은 매 요청에 포함됩니다. 나머지는 `fileMatch`(특정 파일을 읽을 때만), `auto`(요청과 설명이 맞을 때만), `manual`(`#`로 지정할 때만)로 바꾸세요. ([실습 ①](./01-steering.md))
- **단순한 질문·수정에는 서브에이전트나 리뷰 오케스트레이터를 쓰지 마세요.** 에이전트마다 자기 컨텍스트를 읽으므로 비용이 커집니다.
- **린트·포맷 같은 반복 검증은 `command` 타입 Hook으로 하세요.** 모델을 호출하지 않습니다. `agent` 타입 Hook은 자주 발동하는 이벤트(저장 시마다 등)에 걸면 비용이 쌓입니다. ([실습 ⑤](./05-hooks.md))
- **작은 수정은 Spec 대신 일반 대화로 하세요.** Spec(요구사항 → 설계 → 태스크)은 토큰을 많이 씁니다.
- **출력이 긴 명령은 필요한 부분만 보이게 하세요.** 빌드 로그 같은 출력이 그대로 컨텍스트에 쌓입니다.

> 💡 어떤 습관이 사용량을 많이 쓰는지는 Kiro의 사용량 화면에서 확인하고 조정하는 것이 가장 정확합니다.

## 사전 지식

Kiro의 기능(Steering, Spec, Agent, Skill, Hook)이 처음이라면, 각 실습 문서의 "개념" 절에서 그 기능만 필요한 만큼 설명하므로 별도 선행 학습 없이 바로 시작할 수 있습니다.
