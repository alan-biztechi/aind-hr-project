h2. 0. 이 실습에서 배우는 것

* Kiro에게 *"기존 패턴을 학습시켜" 같은 스타일로* 새 코드를 만들게 하는 법
* MyBatis 레이어(Controller → Service → {{@Mapper}} → XML) 4곳을 한 기능으로 관통하기
* 추측이 아니라 *실제 코드·실제 응답*을 근거로 기능을 완성하는 흐름

{tip}
*왜 "Feature Builder"인가*: 실무에서 기능 추가는 "맨땅"이 아니라 *기존 컨벤션을 이어받는* 일입니다. 핵심은 Kiro에게 \*무엇을 만들지\*만 말하는 게 아니라 \*어떤 기존 코드를 본보기로 삼을지\* 지정하는 것입니다.
{tip}

h2. 1. 현재 코드 파악 (출발점)

이 프로젝트의 직원 조회는 이미 이렇게 되어 있습니다. *새 기능은 이 패턴을 그대로 따릅니다.*

레이어 4곳:

||레이어||파일||기존 메서드(본보기)||
|Controller|{{EmployeeController.java}}|{{getEmployeeList()}} → {{GET /v1/employees}}|
|Service|{{EmployeeService.java}}|{{getEmployeeList()}}|
|Mapper 인터페이스|{{EmployeeRepository.java}} ({{@Mapper}})|{{selectAllWithDepartment()}}|
|Mapper XML|{{mapper/EmployeeMapper.xml}}|{{<select id="selectAllWithDepartment">}}|

응답 타입은 부서명이 포함된 {{EmployeeResponse}}(이미 존재)를 재사용합니다.

{tip}
*실무 팁 — 먼저 "본보기"를 정하라*: 비슷한 기능이 이미 있으면 그걸 복제·변형하는 게 가장 빠르고 일관적입니다. 여기선 {{selectAllWithDepartment}}(부서 조인 목록 조회)가 검색의 본보기입니다. 조건({{WHERE name LIKE ...}})만 더하면 됩니다.
{tip}

h2. 2. 요구사항 정의

* 엔드포인트: {{GET /v1/employees/search?name=\{검색어\}}}
* 동작: 이름 *부분 일치*({{LIKE}}), 앞뒤 *공백 trim*
* 빈 검색어({{name}} 없음/공백): *전체 목록 반환*(정책 — 팀에 맞게 바꿔도 됨)
* 응답: 기존 목록과 동일하게 *부서명 포함 {{EmployeeResponse}}* 리스트
* 제약: 기존 컨벤션 유지, SQL 인젝션 안전({{#\{\}}})

h2. 3. Kiro에게 요청하기 (핵심)

에이전트에게 *본보기를 지정*해서 요청합니다. 그냥 "검색 기능 만들어"가 아니라:

{code}
직원 이름 검색 기능을 추가해줘.
- 엔드포인트: GET /v1/employees/search?name=
- EmployeeController의 getEmployeeList, EmployeeService의 getEmployeeList,
  EmployeeRepository.selectAllWithDepartment, EmployeeMapper.xml의 selectAllWithDepartment
  를 본보기로 삼아 "같은 스타일"로 만들어줘.
- 이름 부분 일치(LIKE), 앞뒤 공백 trim, 빈 검색어면 전체 반환.
- 응답은 부서명 포함 EmployeeResponse 재사용.
- MyBatis는 #{} 바인딩만 사용(${} 금지). 백엔드 기존 컨벤션 유지.
{code}

{tip}
*실무 팁 — 프롬프트에 "제약"을 함께 박아라*: {{#\{\} 사용}}, {{기존 컨벤션 유지}} 같은 제약을 *처음부터* 명시하면 재작업이 줄어듭니다. 특히 보안(인젝션) 제약은 매번 명시하는 습관을 들이세요.
{tip}

h2. 4. 구현 결과 (정답 코드)

Kiro가 만든 결과가 아래와 *같은 형태*인지 확인하세요. (직접 작성해도 됩니다.)

h3. 4-1. Mapper XML — {{EmployeeMapper.xml}}에 추가

{code:language=xml}
<select id="searchByName" parameterType="string"
        resultType="com.aind.hr.model.response.EmployeeResponse">
    SELECT e.id,
           e.name,
           e.email,
           e.phone,
           e.department_id,
           d.name AS department_name,
           e.position,
           e.hire_date,
           e.status,
           e.created_at,
           e.updated_at
    FROM employee e
    INNER JOIN department d ON e.department_id = d.id
    <if test="name != null and name != ''">
        WHERE e.name LIKE CONCAT('%', #{name}, '%')
    </if>
    ORDER BY e.id
</select>
{code}

{warning}
*인젝션 주의*: {{LIKE '%$\{name\}%'}}(달러)로 쓰면 SQL 인젝션에 뚫립니다. 반드시 {{CONCAT('%', #\{name\}, '%')}}(샵) 형태로. 이 프로젝트 전 매퍼가 {{#\{\}}}만 쓰는 이유입니다.
{warning}

{tip}
*동적 SQL 팁*: {{<if>}}로 빈 검색어면 {{WHERE}}를 아예 빼서 전체 반환이 됩니다. 조건이 여러 개면 {{<where>}} 태그를 쓰면 {{AND}}/{{OR}} 접두사를 알아서 정리해 줍니다.
{tip}


h3. 4-2. Mapper 인터페이스 — {{EmployeeRepository.java}}에 추가

{code:language=java}
List<EmployeeResponse> searchByName(@Param("name") String name);
{code}

{warning}
*XML id = 메서드명*: {{<select id="searchByName">}}와 인터페이스 메서드명이 *정확히 일치*해야 합니다. 다르면 런타임에 {{Invalid bound statement}} 에러가 납니다(컴파일은 통과 → 실행 시 터짐).
{warning}


h3. 4-3. Service — {{EmployeeService.java}}에 추가

{code:language=java}
public List<EmployeeResponse> searchEmployeesByName(String name) {
    String keyword = (name == null) ? null : name.trim();
    return employeeRepository.searchByName(keyword);
}
{code}

h3. 4-4. Controller — {{EmployeeController.java}}에 추가

{code:language=java}
@GetMapping(value = "/search", produces = MediaType.APPLICATION_JSON_VALUE)
@Operation(summary = "직원 이름 검색", description = "이름 부분 일치로 직원을 검색합니다.")
public ResponseEntity<List<EmployeeResponse>> searchEmployees(
        @RequestParam(required = false) String name) {
    return ResponseEntity.ok(employeeService.searchEmployeesByName(name));
}
{code}

{warning}
*{{/search}}와 {{/\{id\}}}의 관계*: Spring MVC는 더 구체적인 경로를 우선하므로, {{@GetMapping("/search")}}가 등록돼 있으면 {{/\{id\}}}보다 먼저 선택됩니다. 메서드를 클래스 안 어디에 두든 상관없습니다. 오히려 흔한 실수는 *매핑이 아직 반영되지 않은 상태로 호출*하는 것입니다. 이때 {{/v1/employees/search}}는 {{/\{id\}}}로 처리되어 {{"search"}}를 {{Integer}}로 바꾸지 못하고 *400 에러*가 납니다. {{/search}} 호출이 400이면 코드 오류보다 *재시작 누락*을 먼저 의심하세요.
{warning}


{tip}
*LIKE 와일드카드*: 검색어에 {{%}}나 {{_}}가 들어 있으면 {{LIKE}}에서 와일드카드로 해석됩니다({{name=%}}는 전체가 나옴). SQL 인젝션은 아니므로 이 실습에서는 그대로 두지만, 실무에서 "문자 그대로" 검색해야 한다면 이스케이프 처리를 별도로 설계하세요.
{tip}

h2. 5. 검증 (바로 따라 하기)

먼저 프로젝트 루트에서 컴파일과 기존 테스트를 확인합니다.

{code:language=bash}
./mvnw compile   # 문법/타입 오류 확인
./mvnw test      # 기존 테스트 회귀 확인 (로컬 MySQL을 켜 둔 상태에서 실행)
{code}

{tip}
{{./mvnw test}}에는 스프링 컨텍스트를 띄우는 테스트({{HrApplicationTests}})가 있고, 테스트 설정도 로컬 MySQL의 {{aind_sample_db}}를 가리킵니다. [실습 ⓪|실습 ⓪. 시작하기 — 실습 환경 준비]에서 MySQL과 초기 데이터를 준비해 두세요. DB가 꺼져 있으면 이 테스트가 실패할 수 있습니다.
{tip}


{warning}
*컴파일 통과 ≠ 동작 보장*: XML {{id}}와 메서드명이 어긋나는 오류는 컴파일에서 잡히지 않고 *실행 시점*에 터집니다. 그래서 아래 호출 검증이 반드시 필요합니다.
{warning}


그다음 백엔드를 재시작하고 실제로 호출합니다.

{code:language=bash}
./mvnw spring-boot:run   # 또는 IDE 재시작

# 부분 일치
curl -s "http://localhost:8080/v1/employees/search?name=김" | jq .

# 결과 없음 → 빈 배열 []
curl -s "http://localhost:8080/v1/employees/search?name=존재하지않음" | jq .

# 빈 검색어 → 전체 반환
curl -s "http://localhost:8080/v1/employees/search" | jq 'length'

# 앞뒤 공백 → trim 후 검색 (URL 인코딩 %20)
curl -s "http://localhost:8080/v1/employees/search?name=%20김%20" | jq '.[0].name'
{code}

* ☐ {{김}} 검색 시 "김"이 포함된 직원만 나온다
* ☐ 없는 이름은 {{\[\]}} (null이나 에러가 아님)
* ☐ 빈 검색어는 전체 수 반환
* ☐ 응답에 {{departmentName}}이 포함된다 (부서 조인 유지)

{tip}
*실무 팁 — Swagger로도 확인*: {{http://localhost:8080/swagger-ui.html}}에서 {{employee}} 태그에 {{GET /v1/employees/search}}가 새로 떠 있고 {{@Operation}} 설명이 보이면, 문서화까지 자동으로 된 것입니다.
{tip}

h2. 6. 실무 가이드 — 기능 추가 시 유의사항·체크사항·꿀팁

여기부터는 실습을 넘어 *실무 과제에 바로 적용*할 때의 기준입니다. 예시는 이 실습의 직원 검색 API에서 가져왔습니다.

h3. 6-1. 착수 전에 확인할 것

* ☐ 본보기로 삼을 *기존 기능*(Controller·Service·Repository·XML 4곳)을 찾았는가?
* ☐ 응답 모델을 *재사용*할지 새로 만들지 정했는가? (필드가 같으면 재사용, 이 실습은 {{EmployeeResponse}} 재사용)
* ☐ *빈 값·결과 없음·잘못된 입력*의 정책을 정했는가? (예: 빈 검색어 → 전체, 결과 없음 → {{200}} + {{\[\]}})
* ☐ 따라야 할 Steering(보안·엔지니어링 규칙)을 확인했는가? ({{#\{\}}} 바인딩, 기존 컨벤션, 새 의존성 금지)
* ☐ *DB 스키마 변경이 필요한가?* 필요하면 이 실습의 범위를 벗어납니다. 스키마 변경은 리뷰된 마이그레이션 스크립트로만 하고, 공유 DB에 직접 DDL을 실행하지 않습니다.

h3. 6-2. 유의사항 (자주 틀리는 지점)

||구분||유의사항||이 실습의 근거/예시||
|호환성|*추가만 하고 기존 메서드는 수정하지 않는다*|{{GET /v1/employees}}는 그대로 동작해야 함|
|연결|XML {{id}} = 인터페이스 메서드명, {{namespace}} = Repository 전체 클래스명|어긋나면 런타임 {{Invalid bound statement}}|
|보안|사용자 입력은 {{#\{\}}}로만 바인딩한다. {{$\{\}}}는 쓰지 않는다|{{CONCAT('%', #\{name\}, '%')}}|
|책임 분리|입력 정리({{trim}})는 Service, 조건 분기는 XML {{<if>}}에 둔다|4-3, 4-1|
|트랜잭션|읽기 전용 조회는 기존 조회 메서드와 같은 방식으로 둔다|{{EmployeeService}}의 기존 조회 메서드는 {{@Transactional}}을 쓰지 않음|
|응답|목록 조회의 결과 없음은 {{404}}가 아니라 *{{200}} + 빈 배열*로 통일한다|5절 두 번째 curl|
|문서화|Controller에 {{@Operation}}을 달아 Swagger에 노출한다|4-4|
|성능|{{LIKE '%…%'}}는 인덱스를 타지 못한다. 데이터가 커지면 앞 일치나 전문 검색을 검토한다|실습 데이터 규모에서는 문제없음|
|검증|컴파일 통과만으로 완료라고 하지 않는다. 호출 검증까지 한다|5절|
|환경|검증 호출은 *로컬 백엔드·로컬 DB*에만 한다|공유/운영 DB에는 실행하지 않음|

{warning}
*실행하지 않은 검증을 "통과"라고 쓰지 마라*: {{./mvnw test}}나 curl을 실제로 돌리지 못했다면 못 했다고 적습니다. AI의 "문제없어 보입니다"는 검증이 아닙니다.
{warning}


h3. 6-3. 완료 전 체크리스트 (리뷰어용)

* ☐ {{./mvnw compile}} 통과
* ☐ {{./mvnw test}} 통과 (기존 테스트 회귀 없음)
* ☐ curl 4종(부분 일치 / 결과 없음 / 빈 검색어 / 공백 trim)을 실제로 확인했다
* ☐ {{git status}}의 변경 파일이 *4개*(Controller, Service, Repository, Mapper XML)뿐이다
* ☐ 기존 메서드와 기존 쿼리가 수정되지 않았다 ({{git diff}}에 삭제/변경 줄이 없다)
* ☐ 비밀번호·접속 정보 같은 값이 코드나 프롬프트에 들어가지 않았다

h2. 7. 완료 체크리스트

h2. 8. 흔한 에러 & 해결

||증상||원인||해결||
|{{/search}} 호출이 400|매핑이 반영되기 전 서버로 호출해 {{/\{id\}}}로 처리되고, {{"search"}}를 숫자로 바꾸지 못함|서버를 재시작하고 Controller에 {{@GetMapping("/search")}}가 있는지 확인|
|{{Invalid bound statement (not found)}}|XML {{id}} ≠ 인터페이스 메서드명, 또는 네임스페이스 오타|둘을 정확히 일치, {{namespace}}가 Repository FQCN인지 확인|
|검색어 넣어도 전체가 나옴|{{<if>}} 조건의 {{name}} 파라미터명 불일치|{{@Param("name")}}과 {{#\{name\}}}/{{test="name..."}} 일치|
|결과에 부서명이 null|{{INNER JOIN}} 누락 또는 {{AS department_name}} 별칭 빠짐|본보기 쿼리의 JOIN/별칭 그대로 유지|
|한글 검색이 안 됨|DB/커넥션 문자셋|MySQL {{utf8mb4}}, JDBC URL 인코딩 확인|

h2. 9. 돌아보기

* *"본보기 지정"이 핵심*이었습니다. 기존 메서드를 가리키며 "같은 스타일로"라고 하면, Kiro가 네이밍·레이어·에러 규약을 알아서 맞춥니다.
* 이 검색 기능은 [실습 ⑤ Reviewer|실습 ⑤. Reviewer — 코드 품질 검증]의 *리뷰 대상*이 됩니다. 직접 만든 코드를 리뷰받으면 인젝션·경로·입력 처리 같은 지적을 바로 체감할 수 있습니다. (검색 기능이 없어도 ⑤는 기존 코드로 진행할 수 있습니다.)
* *다른 프로젝트에 적용할 때*: "레이어 패턴 + 본보기 메서드 + 제약(보안/컨벤션)"을 프롬프트에 함께 주는 방식은 MyBatis가 아니어도(JPA, 다른 언어) 그대로 통합니다.
