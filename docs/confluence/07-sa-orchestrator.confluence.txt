h2. 0. 이 실습에서 배우는 것

* 메인 에이전트가 여러 전문 에이전트를 *서브에이전트로 조율*하는 패턴
* 관점을 나눠(구조/인프라/API/DB) *병렬로 리뷰*하고 리스크를 *통합*하는 법
* 리뷰 결과가 "진짜인지"를 *정답지로 검증*해 환각을 걸러내는 법

{tip}
*단일 리뷰(실습 ⑤)와 뭐가 다른가*: 실습 ⑤는 한 에이전트가 파일 몇 개를 훑습니다. 여기선 *전문 리뷰어 4명*(구조·인프라·API·DB)이 각자 관점으로 파고든 뒤 {{risk-aggregator}} 1명이 중복 제거·심각도 재분류·인과관계 정리까지 합니다. 사람 조직의 "분야별 리뷰 → 리스크 회의"를 그대로 옮긴 것입니다.
{tip}


{tip}
*왜 기본이 "리포트 읽기"인가*: 직접 실행하면 서브에이전트 5개가 각자 코드를 읽고 앞 단계 결과를 이어받아서, 이 과정에서 *Kiro 사용량이 가장 큰 실습*입니다. 저장소에 이미 완성된 샘플 리포트가 있으므로, 먼저 그것으로 "결과를 검증하는 법"을 익히고 직접 실행은 선택으로 둡니다.
{tip}

h2. 1. 멀티에이전트 오케스트레이션 개념

* *메인(오케스트레이터)*: 사용자가 활성화한 에이전트. {{subagent}} 도구로 다른 에이전트를 띄운다.
* *서브에이전트*: 독립 컨텍스트에서 실행 → 결과만 메인에 반환. *메인 대화를 공유하지 않음*.
* 따라서 메인은 각 서브 호출 프롬프트에 *필요한 맥락(범위 + 이전 findings)을 직접 담아* 전달해야 한다.

{code}
사용자 요청
  → sa-orchestrator (메인)
    → architecture-reviewer        (구조/설계/SPOF)
      → infra-reviewer ∥ api-reviewer   (배포/스케일/장애 ∥ 계약/보안/성능) — 병렬
        → db-reviewer              (스키마/쿼리/트랜잭션)
          → risk-aggregator        (중복제거 + 심각도 + 인과관계)
            → GO / CONDITIONAL GO / NO-GO + 리포트
{code}

h2. 2. 이미 구성된 파이프라인 살펴보기

이 프로젝트에는 SA 리뷰 파이프라인이 *이미 구성*되어 있습니다.

* 에이전트 정의: {{.kiro/agents/}} — {{sa-orchestrator}} + 서브에이전트 5개(리뷰어 4개 + {{risk-aggregator}})
* 설명 문서: {{.kiro/docs/README.md}}
* 검증 가이드(정답지 포함): {{.kiro/docs/TESTING.md}}
* 정적 검증 스크립트: {{.kiro/docs/validate_agents.py}}
* 샘플 리포트: {{.kiro/reports/architecture-review-20261023-142313.md}}

h3. 핵심 설정 포인트 (왜 이렇게 했는가)

||설정||값||이유||
|메인의 {{tools}}|{{subagent/<이름>}} 5개(리뷰어 4 + {{risk-aggregator}})|*서브에이전트를 띄울 수 있게 하고, 띄울 수 있는 대상을 이 5개로 제한* ({{subagent}}만 쓰면 모든 에이전트를 띄울 수 있음)|
|메인 {{permissions}}|{{fs_write}}는 {{.kiro/reports/\*\*}}만 allow|메인만 리포트 쓰기 가능|
|메인 {{permissions}}의 {{subagent}} 규칙|{{match}}에 위 5개 이름, {{effect: allow}}|시작할 때 승인창이 안 뜨게 (서브에이전트의 *도구 호출* 승인과는 별개)|
|리뷰어 {{permissions}}|{{fs_read}} allow, {{fs_write}} deny|리뷰어는 *코드 수정 불가*(읽기 전용)|

{tip}
*V3 전용 설정입니다*: 이 에이전트들은 {{(v3 format)}}으로 표시되는 V3 전용 형식입니다. CLI V3는 예전 방식인 {{toolsSettings.subagent}}({{availableAgents}}/{{trustedAgents}})를 *무시*하므로 위처럼 {{tools}}와 {{permissions}}에 적습니다. CLI는 반드시 {{--v3}}로 실행하세요(아래 5절). V2 하네스는 {{permissions}}를 읽지 않습니다.
{tip}


{tip}
*실무 팁 — 리뷰어는 읽기 전용으로 묶어라*: 리뷰 담당 에이전트에 쓰기 권한을 주지 않으면, 리뷰 중 실수로 코드를 바꿀 일이 원천 차단됩니다. 권한을 좁히는 게 멀티에이전트 안전의 핵심입니다.
{tip}


{warning}
*서브에이전트 도구 제약*: 서브에이전트는 {{read}}/{{write}}/{{shell}}/MCP만 쓸 수 있고 *grep/glob 전용 검색 도구는 못 씁니다.* 그래서 리뷰어들은 파일 탐색을 {{shell}}의 {{grep}}/{{ls}}로 하도록 프롬프트에 적혀 있습니다.
{warning}

h2. 3. 실행 전 정적 검증 (값싼 확인부터)

AI를 부르지 않고 설정이 깨지지 않았는지 1초 만에 확인합니다.

{code:language=bash}
python3 .kiro/docs/validate_agents.py
# PROBLEMS: (none) 이면 로딩 단계 문제 없음
{code}

Kiro CLI의 공식 검증 명령으로도 확인할 수 있습니다. 설정에 문제가 없으면 아무것도 출력되지 않고, 문제가 있으면 오류 메시지가 나옵니다.

{code:language=bash}
kiro-cli agent validate --path .kiro/agents/sa-orchestrator.json
{code}

{tip}
{{validate_agents.py}}는 {{.kiro/agents/\*.json}}만 검사합니다. 같은 폴더에 있는 {{sa-reviewer.md}}(단일 아키텍트 리뷰어, 이 실습의 파이프라인과 별개)는 검사 대상이 아닙니다.
{tip}


로딩 확인:

{code:language=bash}
kiro-cli agent list   # Workspace 항목에 sa-orchestrator + 서브에이전트 5개가 (v3 format) 표시와 함께 보여야 함 (kiro_default 등 내장 에이전트도 함께 보임)
{code}

h2. 4. 샘플 리포트로 검증하기 (기본)

AI를 호출하지 않고, 이미 만들어진 리포트를 *정답지로 검증*합니다.

{{.kiro/reports/architecture-review-20261023-142313.md}}를 엽니다. 구성은 이렇습니다.

||부분||볼 것||
|머리말|대상, 일시, *최종 판정*(이 리포트는 {{NO-GO}})|
|요약|핵심 블로커|
|리뷰어별 findings (2.1\~2.4)|구조 / 인프라 / API / DB 관점의 지적이 어떻게 갈리는가|
|통합 리스크 표|{{risk-aggregator}}가 중복을 합친 결과. 집계는 Critical 5 · High 9 · Medium 8 · Low 3 (총 25건)|
|인과관계|근본 원인 → 파생 리스크의 연결|
|최종 의견|판정 근거와 우선 조치 순서|

h3. 4-1. 정답지 대조

{{.kiro/docs/TESTING.md}}의 정답지로 *반드시 대조*하세요. 정답지는 [실습 ⑤ 3절|실습 ⑤. Reviewer — 코드 품질 검증]의 표와 같은 기준입니다.

* *나와야 함* (실제 코드에 있는 리스크): DB 비밀번호 평문 하드코딩(키: {{spring.datasource.password}}), 전 Service {{@Transactional}} 부재, 예외 처리 비일관(일부 메서드만 try-catch)
* *나오면 안 됨* (환각 신호): 매퍼 XML {{$\{\}}} SQL 인젝션(이 프로젝트엔 {{$\{\}}}가 없음), "입력 검증 전무"(생성/수정 요청엔 {{@Valid}}가 이미 적용됨)

리포트에서 해당 항목을 찾는 명령입니다(AI 사용 없음).

{code:language=bash}
R=.kiro/reports/architecture-review-20261023-142313.md

grep -n "최종 판정" $R              # 판정
grep -n "Transactional" $R | head -3  # 트랜잭션 부재가 나왔는가
grep -n "catch" $R | head -5          # 광범위 catch가 나왔는가
grep -n '\${' $R                      # ${} 관련 줄 — 지적이 아니라 '사용 0건' 확인 문장이어야 함
{code}

{warning}
*비밀번호 항목은 {{grep}}으로 찾지 말고 통합 리스크 표의 RISK-5 행에서 눈으로 확인하세요.* 리포트에 자격증명 값이 그대로 적혀 있어서, 검색 결과가 화면에 값을 그대로 출력합니다. (리뷰 결과에 비밀 값을 옮겨 적지 않는 것이 이 프로젝트의 보안 규칙입니다.)
{warning}


h3. 4-2. 직접 판단해 보기

정답지는 "있어야 할 것 / 없어야 할 것"만 알려 줍니다. 그 밖의 지적은 *스스로 근거를 확인*해야 합니다.

# *RISK-16 "입력검증 부재"*: 정답지의 "입력 검증 전무"와 같은 말일까요? 리포트가 구체적으로 무엇이 없다고 하는지 읽고, {{grep -rn "@Valid" src/main/java}}로 실제 적용 위치를 확인해 보세요.
# *RISK-5 "운영과 동일 DB"*: 이 지적은 테스트 설정이 *운영 DB*를 가리킨다는 전제에서 Critical로 분류됩니다. 코드와 설정에서 그 DB가 운영 DB라는 근거를 찾을 수 있나요? {{.kiro/steering/security-rules.md}}의 "프로덕션" 정의와 대조해 보세요.

{tip}
*실무 팁 — 정답지 없는 리뷰는 신뢰하지 마라*: LLM 리뷰는 매번 조금씩 다르고 가끔 없는 문제를 지어냅니다. "반드시 잡혀야 할 것 + 잡히면 안 되는 것"을 미리 정의해 두면, 리뷰 품질을 *객관적으로* 측정할 수 있습니다. 위 2번처럼 정답지에 없는 지적은 *근거를 직접 확인*하는 습관도 필요합니다.
{tip}

h2. 5. 직접 실행해 보기 (선택)

새 리포트를 직접 만들어 봅니다. 서브에이전트 5개가 순서대로 실행되므로 시간이 걸리고 *사용량이 큽니다.*

1. *메인 에이전트를 {{sa-orchestrator}}로 전환*
* IDE: 채팅 입력창 하단 에이전트 드롭다운 → Workspace 그룹 → {{sa-orchestrator}}
* CLI: {{kiro-cli chat --v3 --agent sa-orchestrator}}

{warning}
*전환이 필수입니다.* 기본(Default) 에이전트로 요청하면 {{sa-orchestrator}}의 {{subagent}} 설정이 적용되지 않습니다.
{warning}


{warning}
*IDE에서는 Autopilot 모드여야 합니다.* 서브에이전트와 병렬 실행은 Autopilot에서 동작합니다({{.kiro/docs/README.md}} 참고). Supervised 모드에서는 서브에이전트가 뜨지 않을 수 있습니다.
{warning}


2. *리뷰 요청 — 범위를 좁혀서 요청하세요*
{code}
출퇴근 기능(AttendanceController, AttendanceService, AttendanceMapper, attendance 테이블)에
범위를 한정해서 아키텍처 리뷰해줘. 범위 밖 파일은 읽지 않아도 돼.
{code}
오케스트레이터는 전체 시스템뿐 아니라 신규 기능이나 변경처럼 *일부 범위의 리뷰 요청*도 받도록 작성되어 있습니다. 범위를 좁히면 서브에이전트가 읽는 양이 줄어듭니다. 전체를 보고 싶다면 {{HR 시스템 전체 아키텍처 리뷰해줘}}로 요청합니다.

3. 진행 관찰
* architecture → (infra ∥ api) → db → risk-aggregator 순으로 스폰
* CLI는 {{Ctrl+G}}로 서브에이전트 실행 모니터를 열어 관찰 가능

4. 결과 확인

리포트는 {{.kiro/reports/architecture-review-<timestamp>.md}}에 생성됩니다.

{code:language=bash}
ls -la .kiro/reports/
{code}

{warning}
*이 폴더에는 이미 샘플 리포트가 있습니다.* 실행 후에는 *새 타임스탬프의 파일이 생겼는지* 확인하세요. 기존 파일만 보고 성공으로 오해하기 쉽습니다.
{warning}


새 리포트도 *4절과 같은 방법*으로 정답지에 대조합니다. 범위를 좁혔다면 범위 밖 항목(예: 직원 삭제)은 나오지 않는 것이 정상이고, 정답지의 모든 항목이 나와야 하는 것은 아닙니다.

h2. 6. 완료 체크리스트

*기본*
* ☐ {{validate_agents.py}}가 PROBLEMS none
* ☐ 샘플 리포트의 구성(판정·리뷰어별 findings·통합 리스크·인과관계)을 확인했다
* ☐ 정답지 "나와야 함"(비밀번호·{{@Transactional}}·예외 비일관)이 리포트에 있는 것을 확인했다
* ☐ 정답지 "나오면 안 됨"({{$\{\}}} 지적, "입력 검증 전무")이 지적으로 나오지 않았음을 확인했다
* ☐ RISK-16, RISK-5를 근거를 찾아 스스로 판단했다

*선택*
* ☐ {{sa-orchestrator}}로 전환해 범위를 좁힌 리뷰를 실행했다
* ☐ 서브에이전트 5개(리뷰어 4 + {{risk-aggregator}})가 스폰되고, *새 타임스탬프의* 리포트가 생성됐다
* ☐ 새 리포트를 정답지와 대조했다

h2. 7. 흔한 문제 & 해결

선택 실행 중에 생기는 문제입니다.

||증상||원인||해결||
|서브에이전트를 못 띄움|메인 {{tools}}에 {{subagent/<이름>}} 없음 / 메인 전환 안 함 / {{--v3}} 없이 실행|{{tools}}에 {{subagent/<이름>}} 추가, 메인을 sa-orchestrator로 전환, {{--v3}}로 실행|
|호출마다 승인창 반복|{{permissions}}의 {{subagent}} 규칙에 이름이 없거나 불일치 / V2 하네스로 실행|{{--v3}}로 실행, 규칙 {{match}}와 에이전트 이름 확인, 급하면 수동 승인|
|리뷰어가 파일을 못 읽음|{{fs_read}}/{{shell}} deny|리뷰어 {{permissions}}의 read/shell allow 확인|
|없는 리스크를 지어냄|프롬프트 과잉 일반화|리뷰어 프롬프트에 "grep 확인 후만 지적" 원칙 추가|
|{{agent list}}에 일부 누락, 또는 {{(v3 format)}} 표시가 없음|V2 스키마/문법 오류, 또는 {{toolsSettings}} 같은 V2 필드가 남음|{{validate_agents.py}}의 PROBLEMS/WARNINGS 확인 → {{/upgrade-agent}}|

h2. 8. 돌아보기

* 아키텍처 검토를 *사람 + 멀티에이전트*로 하면, 관점 분리·병렬·리스크 통합을 자동화하면서도 사람이 최종 판정을 내립니다.
* 리포트가 그럴듯해도 *근거 없는 전제*(예: "운영 DB")가 섞일 수 있습니다. 정답지 대조와 함께 핵심 지적은 코드에서 직접 확인하세요.
* *다른 프로젝트에 적용*: 리뷰어 프롬프트의 "기술 전제"만 그 프로젝트 스택에 맞게 바꾸면 그대로 재사용됩니다. (이 프로젝트는 MyBatis 기준으로 작성됨)
* *Steering + Agent + Workflow + Hooks*를 조합하면 "자동 흐름 속에서 알아서 리뷰하는 조직"으로 확장됩니다.
